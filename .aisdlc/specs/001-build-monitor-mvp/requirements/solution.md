## 1. 结论摘要

- 一句话目标：交付一个可演示、可验证的 Lensmor Monitor MVP，让单用户完成引导、管理 mock 竞品、触发网站监控，并在情报收件箱消费 AI 生成的网站变化分析报告。
- 本次 In / Out 边界：In 是完整 3 步引导、mock 竞品网站、定时与手动刷新、Analysis Report 收件箱、反馈闭环；Out 是社媒分析、Strategic Summary、90 天历史演变、真实竞品站点大规模采集和团队多租户。
- 推荐方案：`Guided Mock Website Monitoring MVP`，用可控 mock 竞品网站和 liteLLM 分析管道先跑通从配置到报告消费的核心闭环。
- 优先验证点：V-001、V-002、V-003。

## 2. 推荐方案

- 方案名：Guided Mock Website Monitoring MVP
- 主流程 / 关键机制：
  - 用户登录后进入完整 3 步 onboarding：选择角色、填写自有产品信息、导入或选择 mock 竞品。
  - 系统为每个 mock 竞品维护基础信息、关联链接、监控状态和可比较的网站快照版本。
  - 用户可手动刷新竞品；后台也按配置周期执行采集任务，生成新快照并与上一快照做差异分析。
  - 差异分析结果连同用户角色、自有产品信息、竞品上下文传入 liteLLM 网关，生成网站变化 Analysis Report。
  - Analysis Report 进入情报收件箱，支持按竞品、优先级、日期范围筛选；打开详情自动标记已读。
  - 用户可对报告提交 Useful、Wrong、Not Important 反馈，反馈进入后续分析质量验证。
- 关键边界 / 取舍：
  - 采用 mock 竞品网站作为监控对象，降低真实站点反爬、页面漂移和外部可用性风险。
  - 首版只做 Analysis Report，不做 Strategic Summary 和历史演变深度分析。
  - 单用户登录与默认数据归属满足 MVP 安全边界，不引入团队、组织、授权协作模型。
  - liteLLM 网关与 key 通过环境变量或安全配置注入，仓库不保存明文密钥。
  - 定时任务和手动刷新都进入同一采集分析任务模型，避免两套生成逻辑。
- 为什么选它：
  - 原始需求的核心价值是把手动竞品调研变成结构化情报卡片，推荐方案直接覆盖“配置竞品 -> 采集变化 -> AI 分析 -> 收件箱消费”的最短价值闭环。
  - 用户已裁决 MVP 主线为“网站监控 + 情报收件箱闭环”，并指定 mock 竞品网站、定时任务、手动刷新和 liteLLM 分析。
  - 该方案保留完整 onboarding，能验证角色和自有产品上下文是否真正提升报告相关性。

## 3. 备选方案

### 3.1 备选方案：Frontend Demo First

- 核心机制：先用全量模拟数据实现页面与交互，不接入真实任务调度或 liteLLM。
- 主流程：
  - 用户完成 onboarding。
  - 系统展示预置竞品、预置报告和预置反馈状态。
  - 页面支持筛选、详情、已读和反馈交互。
  - 后续再替换为真实采集与 AI 管道。
- 边界与取舍：
  - 交互验证速度最快。
  - 无法验证 AI 报告质量、任务状态和刷新链路。
- 适用前提：需要在极短时间内做产品走查，且不要求证明采集分析链路可运行。
- 不选原因：用户已明确 liteLLM 网关和 key 会提供，MVP 需要验证 AI 生成报告闭环，纯前端 demo 风险过高。

### 3.2 备选方案：Full Intelligence Engine MVP

- 核心机制：首版即接入真实竞品站点、自动发现、定时采集、AI 分析、Strategic Summary、历史演变和反馈学习。
- 主流程：
  - 用户填写自有产品 URL。
  - 系统自动发现竞品和关联链接。
  - 后台周期性采集真实网站、社媒和历史归档。
  - AI 生成 Analysis Report、Strategic Summary 和长期演变分析。
  - 用户在收件箱消费并反馈。
- 边界与取舍：
  - 最贴近完整产品愿景。
  - 对采集稳定性、外部服务、成本、安全和排障要求显著增加。
- 适用前提：已有成熟采集基础设施和可控真实数据源。
- 不选原因：首版目标是 MVP，用户已裁决使用 mock 竞品网站，并将社媒、战略总结、历史演变排除在首版主线外。

### 3.3 备选方案：Manual Analyst Workflow

- 核心机制：不做定时任务，用户手动上传或编辑竞品变化，系统只负责 AI 分析和收件箱展示。
- 主流程：
  - 用户完成 onboarding 并添加竞品。
  - 用户手动提交变化内容。
  - liteLLM 生成 Analysis Report。
  - 报告进入收件箱供用户查看和反馈。
- 边界与取舍：
  - 实现采集成本最低。
  - 无法验证“自动化监控”价值主张。
- 适用前提：MVP 只验证 AI 分析文本质量，不验证监控机制。
- 不选原因：原始需求强调周期性采集和手动刷新，用户也已要求定时任务 + 手动刷新。

## 5. 验证清单

- V-001 liteLLM 网关配置与报告质量
  - 风险/假设：liteLLM 网关可稳定生成结构化 Analysis Report，且输出包含变更摘要、战略意图和行动建议。
  - 方法：研发负责人用 3 组 mock 竞品快照调用网关，记录响应时间、失败率和字段完整度。
  - 成功/失败信号：3 组样例均生成完整报告，接口失败率低于 5%，单次生成耗时不超过 30 秒；否则失败。
  - Owner：研发负责人
  - 截止：方案评审后 2 个工作日
  - 触发动作：失败则降低首版报告结构复杂度，并增加重试与人工兜底文案。

- V-002 mock 竞品网站变化样例覆盖度
  - 风险/假设：mock 网站快照能够覆盖 MVP 需要展示的关键变化类型，足以验证收件箱价值。
  - 方法：产品负责人定义不少于 5 个变化样例，覆盖文案、定价、功能、页面结构和 CTA 调整。
  - 成功/失败信号：每个样例都能产生可读差异和可解释的业务含义；若少于 4 类有效变化则失败。
  - Owner：产品负责人
  - 截止：PRD 评审前
  - 触发动作：失败则补充 mock 快照库，或缩小首版变化类型声明。

- V-003 定时任务与手动刷新共用任务模型
  - 风险/假设：定时任务和手动刷新可以复用同一采集分析任务模型，避免状态与报告生成逻辑分叉。
  - 方法：研发负责人设计任务状态机并用 1 个定时触发、1 个手动触发样例走通。
  - 成功/失败信号：两类触发都能进入统一状态流并生成报告；若出现重复报告、状态不一致或无法追踪失败原因则失败。
  - Owner：研发负责人
  - 截止：设计评审前
  - 触发动作：失败则先保留手动刷新为主路径，定时任务降级为触发器封装。

- V-004 单用户登录的安全边界
  - 风险/假设：单用户登录足以满足 MVP 的访问保护，不需要完整多租户。
  - 方法：研发负责人列出受保护页面和接口，测试负责人验证未登录访问、登录后访问、退出后访问。
  - 成功/失败信号：核心页面和报告接口未登录均不可访问；否则失败。
  - Owner：研发负责人；测试负责人
  - 截止：实现计划评审前
  - 触发动作：失败则收紧路由守卫和接口鉴权，暂不增加团队授权模型。

- V-005 项目现有架构入口缺失
  - 风险/假设：当前仓库缺少可识别的应用入口和项目知识库，后续设计与实现计划需要先确定技术栈和模块落点。
  - 方法：研发负责人在设计调研中确认仓库真实入口、技术栈、运行命令、测试命令和部署边界。
  - 成功/失败信号：能形成可执行的设计与实现计划；若仍无法定位应用入口则失败。
  - Owner：研发负责人
  - 截止：设计调研完成前
  - 触发动作：失败则先补项目骨架决策，再拆分实现任务。

## Impact Analysis

### 受影响模块

- Onboarding
  - 影响类型：新增能力。
  - 关键不变量：首次进入必须完成角色、自有产品信息、竞品导入 3 步；输出需要进入 AI 分析上下文。
  - stale：no，来源为 `requirements/raw.md` 与 R1 澄清记录。
- Auth
  - 影响类型：新增能力。
  - 关键不变量：单用户登录保护核心页面和接口；不引入团队多租户。
  - stale：no，来源为 R1 澄清 3。
- Competitor Monitoring
  - 影响类型：新增能力。
  - 关键不变量：竞品可添加、编辑、删除、暂停、恢复、手动刷新；首版监控对象为 mock 竞品网站。
  - stale：no，来源为 `requirements/raw.md` 与 R1 澄清 2。
- Collection Task
  - 影响类型：新增能力。
  - 关键不变量：定时任务与手动刷新应复用同一任务模型；任务支持状态可见、失败可追踪。
  - stale：no，来源为 `requirements/raw.md` 与 R1 澄清 2。
- AI Analysis
  - 影响类型：新增能力 / 外部服务集成。
  - 关键不变量：通过 liteLLM 网关生成 Analysis Report；密钥不得落库或写入仓库。
  - stale：no，来源为 R1 澄清 2 与安全要求。
- Intelligence Inbox
  - 影响类型：新增能力。
  - 关键不变量：首版只承载 Analysis Report；支持卡片列表、筛选、详情、自动已读和反馈。
  - stale：no，来源为 `requirements/raw.md` 与 R1 澄清 5。

### 需遵守的不变量

- MVP 首版范围必须围绕“网站监控 + 情报收件箱闭环”，不能把社媒分析、Strategic Summary、历史演变作为首版阻塞项。
- onboarding 必须完整包含角色、自有产品信息和竞品导入，且这些信息进入报告分析上下文。
- mock 竞品网站是首版采集对象，真实第三方站点采集不作为首版交付前提。
- 定时任务和手动刷新都必须能生成 Analysis Report。
- 单用户登录必须保护核心页面和接口，密钥必须通过安全配置注入。

### 跨模块影响

- Onboarding 产出的角色和自有产品信息会影响 AI Analysis 的提示词上下文和报告解释口径。
- Competitor Monitoring 的状态会影响 Collection Task 是否允许触发采集。
- Collection Task 的成功、失败和重试状态会影响 Intelligence Inbox 中报告是否生成、是否展示错误提示。
- AI Analysis 的输出结构会影响 Inbox 卡片字段、报告详情字段和反馈入口。
- Auth 的登录态会影响 onboarding、竞品、任务、报告和反馈的所有读写入口。
- Context Gaps 会影响设计与实现计划的模块落点，详见 `## Context Gaps`。
