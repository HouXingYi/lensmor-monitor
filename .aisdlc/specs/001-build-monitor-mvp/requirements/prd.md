## 1. 结论摘要

- 目标：让单用户完成 Lensmor Monitor 的完整 3 步引导，管理 mock 竞品网站，通过定时任务或手动刷新生成网站变化 Analysis Report，并在情报收件箱查看与反馈。
- In / Out 边界：In 包含登录、onboarding、mock 竞品管理、采集任务、liteLLM 分析、Analysis Report 收件箱、已读与反馈；Out 包含社媒分析、Strategic Summary、90 天历史演变、真实第三方网站大规模采集、团队多租户。
- MVP 边界：首版以可控 mock 竞品网站验证监控和报告消费闭环；首版只承载 Analysis Report；首版采用单用户登录和默认数据归属。
- 推荐方案：引用 `requirements/solution.md#2-推荐方案` 的 `Guided Mock Website Monitoring MVP`。
- 优先验证点：RISK-001、RISK-002、RISK-003。

## 2. 范围与里程碑

### 2.1 MVP 范围（In / Out）

- In：
  - 单用户登录和退出。
  - 完整 3 步 onboarding：角色选择、自有产品信息填写、导入竞品。
  - mock 竞品网站与竞品档案管理：列表、详情、添加、编辑、删除、暂停、恢复。
  - 关联链接维护：每个竞品最多 10 条。
  - 手动刷新：用户主动触发一次采集分析。
  - 定时任务：系统按配置周期触发采集分析。
  - 网站快照差异分析：比较当前 mock 快照与上一快照，形成结构化差异。
  - liteLLM Analysis Report 生成：包含变更摘要、战略意图、行动建议和原始链接。
  - 情报收件箱：卡片列表、详情、优先级、日期范围、竞品筛选、打开详情自动已读。
  - 情报反馈：Useful、Wrong、Not Important；Wrong 支持错误类型选择。
  - 基础状态与异常反馈：加载中、空数据、任务失败、AI 生成失败。
- Out：
  - 社媒品牌分析。
  - Strategic Summary。
  - 90 天历史差异分析。
  - 真实第三方站点自动发现与大规模采集。
  - 多用户团队、组织、角色授权和跨用户协作。
  - 截图签名链接能力，除非实现中已有轻量能力可直接复用。

### 2.2 里程碑

- MVP：
  - P0 功能全部可用。
  - 用户可从首次登录走到生成并消费至少 1 条 Analysis Report。
  - 手动刷新和定时任务都能进入同一任务状态流。
  - 未登录用户不能访问核心页面和报告接口。
- M1：
  - 扩展真实竞品站点采集。
  - 增加 Strategic Summary。
  - 引入历史演变分析和更完整的反馈学习。

## 3. 核心场景

### 3.1 场景 S-001：首次进入并完成竞品配置

- 触发：单用户首次登录系统，尚未完成 onboarding。
- 参与者：登录用户。
- 目标：完成角色、自有产品信息和竞品导入，使系统获得后续分析上下文。
- 成功标准：
  - 用户完成 3 步 onboarding 后进入产品主界面。
  - 至少 1 个 mock 竞品处于“监控中”状态。
  - 用户填写的角色和自有产品信息可被后续报告生成流程读取。

### 3.2 场景 S-002：触发网站监控并生成 Analysis Report

- 触发：用户点击某竞品的手动刷新，或定时任务到达触发时间。
- 参与者：登录用户；后台任务系统；liteLLM 网关。
- 目标：对 mock 竞品网站生成新快照，与上一快照对比后生成 Analysis Report。
- 成功标准：
  - 任务状态从排队或采集中进入完成或失败状态。
  - 成功任务生成 1 条 Analysis Report 并进入情报收件箱。
  - 失败任务记录失败原因，并在竞品或任务状态中可见。

### 3.3 场景 S-003：在情报收件箱消费并反馈报告

- 触发：用户打开情报收件箱。
- 参与者：登录用户。
- 目标：用户筛选、阅读、理解并反馈网站变化 Analysis Report。
- 成功标准：
  - 用户能按竞品、优先级、日期范围筛选报告。
  - 用户打开报告详情后，该报告标记为已读。
  - 用户能提交 Useful、Wrong 或 Not Important 反馈。

## 5. 业务规则与口径

- BR-001：未登录用户不能访问 onboarding、竞品、任务、报告和反馈相关页面或接口。
- BR-002：首次登录且未完成 onboarding 的用户必须进入 3 步 onboarding；完成后进入主界面。
- BR-003：角色选项包含产品营销经理、产品经理、市场营销经理、创始人、投资人、其他。
- BR-004：自有产品信息至少包含名称、URL、一句话描述、目标受众、核心卖点、竞争优势和当前阶段战略目标。
- BR-005：每个竞品必须有名称和主域名；关联链接最多 10 条。
- BR-006：竞品状态包含监控中、已暂停、采集进行中；暂停状态不执行定时采集。
- BR-007：手动刷新可对已暂停竞品禁用，或要求用户先恢复监控。
- BR-008：手动刷新和定时任务必须复用同一任务状态流。
- BR-009：Analysis Report 必须包含变更摘要、战略意图、行动建议、关联竞品、优先级、生成时间和原始链接。
- BR-010：优先级标签包含紧急、中等、低影响。
- BR-011：打开报告详情时自动标记为已读。
- BR-012：Wrong 反馈必须选择错误类型；错误类型包括信息不准确、内容不相关、数据过时、信息重复、战略意图有误、遗漏关键变更、噪音过多、源数据不准确。
- BR-013：liteLLM 网关地址和 key 不写入仓库，不在客户端明文暴露。

## 6. 验收标准（AC）

### 6.1 场景 S-001 的 AC

- AC-001：给定未完成 onboarding 的登录用户，当用户进入系统时，系统展示角色选择步骤；当用户选择任一角色并继续时，系统进入自有产品信息步骤。
- AC-002：给定用户位于自有产品信息步骤，当用户填写名称、URL、一句话描述、目标受众、核心卖点、竞争优势和当前阶段战略目标并提交时，系统保存这些字段并进入竞品导入步骤。
- AC-003：给定用户位于竞品导入步骤，当用户选择或添加至少 1 个 mock 竞品并完成引导时，系统创建竞品记录并进入主界面。
- AC-004：给定用户完成 onboarding，当后续生成 Analysis Report 时，报告生成流程可以读取用户角色和自有产品信息作为分析上下文。

### 6.2 场景 S-002 的 AC

- AC-005：给定一个状态为监控中的竞品，当用户点击手动刷新时，系统创建一条采集分析任务并展示采集进行中状态。
- AC-006：给定定时任务到达触发时间，当竞品状态为监控中时，系统创建一条采集分析任务；当竞品状态为已暂停时，系统不创建任务。
- AC-007：给定任务成功获取 mock 竞品的新快照，当存在上一快照时，系统生成差异摘要并调用 liteLLM 生成 Analysis Report。
- AC-008：给定 liteLLM 调用成功，当报告生成完成时，情报收件箱新增 1 条 Analysis Report 卡片，卡片展示标题、关联竞品、生成时间和优先级。
- AC-009：给定采集或 AI 生成失败，当任务结束时，系统记录失败状态和失败原因，且不会生成空报告。

### 6.3 场景 S-003 的 AC

- AC-010：给定收件箱存在多条 Analysis Report，当用户按竞品筛选时，列表只展示该竞品关联报告。
- AC-011：给定收件箱存在不同优先级报告，当用户选择优先级筛选时，列表只展示匹配优先级的报告。
- AC-012：给定收件箱存在不同日期报告，当用户选择日期范围时，列表只展示生成时间在范围内的报告。
- AC-013：给定一条未读报告，当用户打开报告详情时，系统将该报告标记为已读。
- AC-014：给定用户打开报告详情，当用户点击 Useful、Wrong 或 Not Important 并提交时，系统保存反馈记录。
- AC-015：给定用户选择 Wrong 反馈，当用户未选择错误类型并提交时，系统阻止提交并提示选择错误类型。

### 6.4 安全与可用性 AC

- AC-016：给定未登录访问者，当访问主界面、竞品、任务、报告或反馈接口时，系统拒绝访问并引导登录。
- AC-017：给定列表数据为空，当用户进入竞品列表或收件箱时，系统展示空状态和下一步操作入口。
- AC-018：给定异步任务运行中，当用户查看竞品状态或任务状态时，系统展示加载或采集进行中状态。
- AC-019：给定前端生产构建，当用户打开首屏时，首屏加载时间目标不超过 3 秒。
- AC-020：给定收件箱加载单批报告，当数据量在 MVP 样例范围内时，单批加载时间目标不超过 2 秒。

## 7. 异常与边界

- E-001：liteLLM 网关调用失败时，任务进入失败状态，记录失败原因，报告不进入收件箱。
- E-002：mock 快照没有变化时，任务可记录“未发现有意义变化”，默认不生成 Analysis Report。
- E-003：竞品处于已暂停状态时，定时任务不触发采集；手动刷新入口按产品设计禁用或提示恢复监控。
- E-004：关联链接超过 10 条时，系统阻止保存并提示上限。
- E-005：用户删除竞品时，系统需要处理关联任务和报告的展示策略；MVP 可采用软删除或删除前阻止策略，具体以设计阶段数据模型为准。
- E-006：用户退出登录后，已打开的核心页面再次请求数据时必须被拒绝访问。

## 8. 风险/依赖与验证清单

- RISK-001 liteLLM 网关配置与报告质量
  - 验证信号：3 组 mock 快照均生成包含变更摘要、战略意图、行动建议和原始链接的报告；接口失败率低于 5%；单次生成耗时不超过 30 秒。
  - 方法：研发负责人使用样例快照调用 liteLLM 网关并记录结果。
  - Owner：研发负责人
  - 截止：方案评审后 2 个工作日
  - 触发动作：成立则按当前报告结构进入设计；不成立则降低报告结构复杂度，并增加重试与人工兜底文案。
- RISK-002 mock 竞品网站变化样例覆盖度
  - 验证信号：不少于 5 个变化样例覆盖文案、定价、功能、页面结构和 CTA 调整，其中至少 4 类能生成可解释差异。
  - 方法：产品负责人定义样例，研发负责人验证差异分析输出。
  - Owner：产品负责人；研发负责人
  - 截止：PRD 评审前
  - 触发动作：成立则进入原型和设计；不成立则补充 mock 快照库或缩小变化类型声明。
- RISK-003 定时任务与手动刷新共用任务模型
  - 验证信号：两类触发都进入统一状态流，并能生成报告或失败记录。
  - 方法：研发负责人设计状态机，并用一个定时触发和一个手动触发样例演练。
  - Owner：研发负责人
  - 截止：设计评审前
  - 触发动作：成立则采用统一任务模型；不成立则先保留手动刷新主路径，定时任务降级为触发器封装。
- RISK-004 单用户登录安全边界
  - 验证信号：未登录访问核心页面和报告接口均被拒绝；登录后可访问；退出后再次请求被拒绝。
  - 方法：测试负责人按页面和接口清单执行访问验证。
  - Owner：测试负责人；研发负责人
  - 截止：实现计划评审前
  - 触发动作：成立则维持单用户登录方案；不成立则收紧路由守卫和接口鉴权。
- RISK-005 项目现有架构入口缺失
  - 验证信号：设计调研能固定技术栈、运行命令、测试命令、模块边界和部署边界。
  - 方法：研发负责人扫描仓库并形成设计调研结论。
  - Owner：研发负责人
  - 截止：设计调研完成前
  - 触发动作：成立则进入设计决策；不成立则先补项目骨架决策。

## 9. 原型产出判定

- 交互变化结论：需要原型。原因是 MVP 包含首次引导、竞品管理、任务状态、收件箱筛选、报告详情和反馈，页面流与状态分支会影响研发和测试理解。
- 页面与入口：登录页、onboarding 3 步页面、主应用布局、竞品列表、竞品详情、情报收件箱、报告详情、任务状态反馈、反馈入口。
- 关键控件/字段与校验：
  - onboarding 字段校验：必填字段、URL 格式、至少 1 个竞品。
  - 竞品表单校验：名称、主域名、关联链接上限 10 条。
  - 收件箱筛选：竞品、优先级、日期范围可组合。
  - 反馈提交：Wrong 必须选择错误类型。
